# 0x245000–0x2550A0 (Sony SDK libs: libm, libscf, libmpeg, libipu) — ee-gcc 2.96 session

## Toolchain finding: the bundled ee-gcc 2.96 (2.96-ee-001003-1) is NOT the exact library compiler

Tested on IsT10K, _sceMpegError1, _decodeOrSkip, fabs, copysign (func_0024A738) with
`// SLY2_CC: tools/compilers/ee-gcc2.96` + `-O2 -G0`:

* **Saved-register slot size**: the target uses a 16-byte slot per callee-saved GPR, stored with `sd`
  (IsT10K: frame 0x20, `sd s0,0; sd ra,0x10`; _sceMpegFlush: frame 0x30, s0@0 s1@0x10 ra@0x20;
  _sceMpegError1: frame 0x120, buf 0x100, s0@0x100, ra@0x110). ee-gcc 2.96-ee-001003-1 uses 8-byte slots
  (IsT10K: frame 0x10, `sd s0,0; sd ra,8`). None of -mlong64/-mint64/-mabi=eabi|64|n32/-mips3/-mips4/
  -mgp64/-msplit-addresses/-O1/-O3/-Os/-g/-mcpu=r4000/-msoft-float/-mno-mad change this
  (-mgp32 and -mabi=32 crash cc1 with an ICE; -mabi=o64 gives frame 48; -fno-omit-frame-pointer gives 32 but
  saves $fp). So **any function with a stack frame cannot match with this compiler**.
  (cc1 contains the string "Register precision must be 32, 64, or 128" — the Sony build probably had a
  128-bit register-size mode that sizes save slots as TImode; no option name for it was found in cc1.)
* **Tail calls**: 2.96 emits sibcalls (`j func` with the epilogue first), which the target does in many
  places (_waitIpuIdle). But _decodeOrSkip in the target is NOT a sibcall (jal + `b` to a shared epilogue),
  so libmpeg may have been built with sibcalls off in some files, or the slot-size difference matters.
* Leaf functions (no frame) are the only candidates.

## Session 2 (flag search on leaf/sibcall functions, ee-gcc 2.96-ee-001003-1)

**Conclusion: no flag combination makes the bundled 2.96 reproduce the library compiler; `-O2 -G0` is still the
best setting and only frameless leaf functions without calls can match.** Evidence:

* **Sibcalls always keep a frame**: even `void f(void *a){ g(a, 0x20); }` (func_00254620, target `j g; li a1,0x20`)
  gives `addiu sp,-16; sd ra; ...; ld ra; j g; addiu sp,16`. Tried -O1/-O2/-O3/-Os, -fomit-frame-pointer,
  -fno-optimize-sibling-calls, -fno-delayed-branch, -ffixed-ra/-fcall-used-ra/-ffixed-31, -mentry, -mips3:
  none removes the `$ra` save. (Probably regs_ever_live[31] stays set from the discarded normal-call
  alternative; fixed in Sony's later build.) So **every wrapper/tail-call function in this range is blocked**,
  as are all functions with a frame (16-byte save slots, see above).
* `_waitIpuIdle` (0x252358 and 0x254488): real signature is `void _waitIpuIdle(sceMpeg *mp)` — $a0 is passed
  through untouched to `_sceMpegWaitIpuIdle(mp)` (0x251E60), which is why the target uses $a1 for the mask.
  The unfilled delay slots are natural (nothing can fill them), not a flag. Blocked only by the frame.
* **Return-jump conversion**: sceIpuSync (leaf, switch on mode 0/1): the target jumps to a shared
  `daddu v0,v1; jr ra; nop` (`b end; nop`), the bundled 2.96 turns those jumps into duplicated `jr ra`
  (reorg make_return_insns) and uses `beql`. 11/25 differ; -fno-delayed-branch, -fno-thread-jumps,
  -fno-gcse, -fno-schedule-insns etc. do not change it. -> build/hand_wip/sceIpuSync.c
* **Float literal rounding**: the bundled 2.96 (i386 host) mis-rounds decimal float constants:
  newlib kf_sin.c `S6 = 1.5896910177e-10` -> 0x2F2EC9D2 (target, and correct rounding: 0x2F2EC9D3),
  `S4 = 2.7557314297e-06` -> 0x3638EF1A (target 0x3638EF1B). Also the float->int type pun
  (GET_FLOAT_WORD union) goes through the stack (`swc1/lw`), where the target uses `mfc1`.
  -> build/hand_wip/__kernel_sinf.c (62/65 differ).
* Scheduling / register allocation also differ in leaf code (fabs: target copies x to a1 first and does
  dsra32 immediately; _ch4dma: target rebuilds each DMA register address right before each store,
  2.96 hoists them and uses $at for 0xFFFF0) -> build/hand_wip/_ch4dma.c (49/54).
* Straight-line store code does match: **func_0024B8F8 MATCH** (`p[0]=a; p[1]=b; p[2]=a; p[3]=a;`, natural order).

## Round 9 (gnu-reorder mode retry, 0x246000-0x2550A0)

**Key finding: libm/libmpeg (0x244B68-0x2550A0) = ordinary gcc WITH delayed-branch filling (reorg) + GNU as in reorder mode.**
The current `SLY2_ASM: gnu-reorder` path adds `-fno-delayed-branch`; with that flag removed (same 2.95.3-136 cc1, same
GNU as, loop pinning kept) every existing src/lib match in this range still matches (_decodeOrSkip, _sceMpegStopIpuDma,
tanf, sinf, cosf, _ch4dma, func_00254F00, func_0024B8F8, _sceMpegError, sceMpegAddCallback, sceMpegClearRefBuff,
sceMpegGetPicture, func_0024F770, func_0024A780, func_00249C60, matherr — tested with the gnu-reorder header added),
whereas with -fno-delayed-branch most of them break (e.g. sinf 61/67, _sceMpegError 15/22). Plus two NEW matches:
**sceMpegInit** and **sceIpuSync** (build/hand_wip/, MATCH only in that mode). Evidence: target `beqz` slots filled by
reorg steal-from-target with the insn duplicated (sceMpegInit `lui v0,0x1000`), branch-likely loops (`bnel ..; addiu`),
while volatile stores reorg refuses end up in jal slots via gas (sceMpegInit `sw $zero` in jal sceIpuInit slot).
kCopy/memclr/kputchar (libkernel, 0x2357xx-0x2414xx) still need -fno-delayed-branch, so this should be a SECOND mode
(e.g. `SLY2_ASM: gnu-reorder-db`). Scratch harness reproducing it without editing tools: build/hand_wip/mt2_delayed_branch_check.py
(`DB=1 python3 build/hand_wip/mt2_delayed_branch_check.py FILE.c NAME`; NOPIN=1 skips loop pinning, KEEP=path saves the .s).
Caveat: with DB, pin_loop_branches can produce "problematic short loop for Emotion Engine in noreorder section" (memclr)
when reorg already filled the loop branch — the pinning should skip branches already inside .set noreorder.

Remaining toolchain diff in DB mode (libm): Sony's gas inserts a `nop` between `mfc1 $v0,$fN` and an immediately
following `.set noreorder` branch that reads $v0 (gcc writes `#nop` there), but NOT between mfc1 and a normal reorder-mode
use (`mfc1 v0,f12; daddu a0,v0` at __kernel_cosf entry has no nop). Our 2.96 gas never inserts it. With that one rule
__kernel_cosf (build/hand_wip, newlib kf_cos.c verbatim) would match; __kernel_sinf too (5 diffs, same nop).
-mcpu=r4000 on gas inserts it everywhere (too many). `.p2align 3` labels after `j $31` explain the extra trailing nop.

Still blocked: everything that saves $s regs (16-byte sd slots) and the frameless `j` wrappers (unchanged).
fabs/copysign: pure scheduling (target `daddu v0,a0; dsra32 v0,v0,0` and early low-word copy) — not solved in either mode.
_system_header (build/hand_wip): bitstream skip macro x3; target hoists `ld pos` before the refill loop and keeps
bits in a register; my inline version differs in register/load placement.
