# 0x234F48–0x245000 (Sony SDK libs: libkernel, sif, sceFs, libgcc, libgraph/dma/cdvd/pad/mc) — ee-gcc 2.96 session

## Flag search result: no flag set of the bundled ee-gcc 2.96 reproduces this code

Compiler tested: tools/compilers/ee-gcc2.96 (2.96-ee-001003-1). Test functions: func_00239AB0
(`SetT2(0xB0001000, x)`-style wrapper), serialPutchar, sceFsReset, _waitIpuIdle (0x252358).
Flags tried: -O1/-O2/-O3/-Os, -fno-delayed-branch, -fno-optimize-sibling-calls, -foptimize-sibling-calls,
-fomit-frame-pointer, -fno-schedule-insns, -fno-schedule-insns2 (and both), -fno-gcse, -mcpu=r4000/r5900,
-msplit-addresses, -G0. Results:

1. **Frameless sibcall**: target func_00239AB0 = `daddu a1,a0; lui a0,0xB000; j func_00239A40; ori a0,..`
   (no frame). 2.96 *always* allocates a 16-byte frame and saves/restores `$ra` around a sibcall
   (`subu sp; sd ra; ...; ld ra; j g; addu sp`) — for `f(x){g(K,x);}`, `return g(x);` and
   `if (...) g();` alike, with every flag above. The target compiler has proper leaf detection after
   sibcall conversion (like gcc >= 3.0). => every function whose only call is a tail call is unmatchable.
2. **Constant propagation into branches**: target serialPutchar is
   `if (c != '\n') goto L; kputchar('\r'); kputchar('\n') [sibcall, constant 0xA re-materialised]; L: kputchar(c) [sibcall]`
   with no saved $s0. 2.96 keeps `c` in $s0 (8-byte slot frame) — the target compiler knows c=='\n' on
   that path (jump threading / cprop), again gcc-3-like.
3. **Scheduling**: sceFsReset target `addiu sp; lui v0; lui a0; sd ra; sw zero,..(v0); addiu a0; daddu a1; jal memset; addiu a2,4`.
   2.96 (any sched flag combination) puts `sw` in the jal delay slot or before the `lui a0`.
4. 16-byte callee-save slots (see notes/245000.md) — not reproducible.
5. _waitIpuIdle (0x252358, libipu) has *unfilled* delay slots (`bne; nop`, `j; nop`) — looks like
   `-fno-delayed-branch` + gas reorder, but frameless (point 1), so it does not match either.

6. 2.96 also mis-rounds float constants (floorf: 1e30f -> 0x7149F2C9, target 0x7149F2CA) and its block
   layout/scheduling differs much more from the target than 2.95.3 does (__fpcmp_parts_d: 53/70 differ
   with 2.96, MATCH with 2.95.3).

Conclusion: the libraries were NOT built with 2.96-ee-001003-1. The code generator is essentially
**ee-gcc 2.95.x** (same scheduling, block layout, delay-slot filling as `tools/compilers/bundle/ee-gcc2.95.3-136`
`-O2 -G0` in most functions) plus Sony-specific changes we cannot reproduce: sibcalls with leaf detection,
`sd` saves with 16-byte slots for $s regs, `mult1`, unfilled/extra-padded short-loop delay slots, GNU-as
style 64-bit constant expansion (`ori 0xFFF0; dsll32 16` instead of SN's `addiu -1; dsll32 20`), and no
SN FPU hazard nop between `c.lt.s` and `bc1f`.

### => Use this for the SDK range:

    // SLY2_CFLAGS: -O2 -G0

### Discovery: the SDK libs look like "-fno-delayed-branch + GNU as slot filling"
Every unfilled `bnez/bne ...; nop` short-loop slot in this range fits this model: the compiler (2.95.x code generator)
emitted reorder-mode code without filling delay slots, and GNU as filled each slot by swapping in the preceding
independent instruction (that gives `beqz a2; daddu a3,0`, `jr ra; daddu v0,0`), except where the previous insn feeds the
branch (loop tests -> `nop`). Verified on kCopy: 2.95.3-136 `-fno-delayed-branch -S` output is *instruction-for-instruction*
the target once each `insn; branch` pair is swapped (see build/hand_wip/kCopy.c - only the 3 swaps differ). Our build
assembles with SN ps2eeas which never fills slots, so this can't be reproduced per-file. A toolchain option to assemble
SDK files with a slot-filling GNU as (2.96's ee/bin/as fills slots but also fills the kCopy loop slot, the target's
assembler did not - it probably refused to fill a slot of a backward branch inside a <=7-insn loop (R5900 short-loop
errata)) would unlock kCopy, kCopy_00239898/00239920/0023B238, func_00239518, memclr, sceFsReset,
sceSifLoadFileReset, fptodp and probably many more. The 2.9-ee GNU as.exe in bundle/*/lib/gcc-lib does NOT fill slots.
- Other compilers tried for `sd $sN` with 16-byte slots: 2.95.2-273a/274 and 2.95.3-107/114 give the target's slot
  layout (s0@0, s1@0x10, ra@0x20) but with `sq`; 2.96 gives `sd` with 8-byte slots. No flag (-mgp64, -mips3, -mlong64,
  -mint64, -mcpu=r4000) changes either. None of the bundled compilers emits frameless sibcalls.

## Round 9 (SLY2_ASM: gnu-reorder retry of 0x234F48–0x23C000)

Matched (src/lib, ee-gcc2.95.3-136 -O2 -G0):

- **snprintf_char** (normal mode, no gnu-reorder needed): `-fstrict-aliasing` + `p = *pp; *p++ = c; *pp = p;` (the `lw *left`
  hoisted above the `sw *pp` store needs type-based aliasing).
- **iAllocTimerCounter** (gnu-reorder + `-fstrict-aliasing`): `if (p != 0) {...} return 0x80008005;` layout; only `seq`
  (TS+0xC) and `id` (TC+0x8) volatile; TC+0x28 must be a pointer type (`void *`) and TC+0xC `int` - found by brute force
  over field types/store orders: strict-aliasing alias sets decide the store schedule.

### Discoveries
1. **-fstrict-aliasing**: Sony's SDK compiler evidently had type-based aliasing on (2.96-style default). Try it whenever stores/
   loads of different types are scheduled differently from ours. Field *types* matter (pointer vs int).
2. **Two SDK assembly modes**: libkernel files (DIntr, kCopy, _sceIDC, iAllocTimerCounter, memclr) = `-fno-delayed-branch` + GNU as
   (= current gnu-reorder). But printf (ftoi) and alarm (InsertAlarm: `beql`, slots stolen from branch targets) were compiled
   **with gcc reorg ON**, and GNU as filled the slots reorg left empty (ftoi's `jr ra; dsra32` = split of the sign-extend pair).
   Verified with a scratch pipeline (2.95.3 -S with delayed-branch, then gnu_reorder.assemble): ftoi's tail matches. A
   gnu-reorder variant WITHOUT -fno-delayed-branch (e.g. `SLY2_ASM: gnu-reorder-reorg`) would be needed (tools change, not done).
3. Still wrong with gnu-reorder (toolchain, not source):
   - `$s` register saves: target `sd` in 16-byte slots (s0@0, s1@0x10, ra@0x20); 2.95.x gives `sq`, 2.96 8-byte slots. Bodies of
     AllocTimerCounter / func_0023A3A0 / func_00235110 family match otherwise. Blocks ~90% of the range.
   - frameless `j` sibcalls (serialPutchar, func_00239AC0/AD0, __main__Fv, func_0023A8E8, func_002398D0 ...).
   - scheduling of a global store vs call-argument setup: target issues the store early (sceFsReset, sceSifLoadFileReset,
     supplement_crt0, func_0023A8E8), ours issues it last; isceSifSendCmd `addiu sp` 2 insns early. No 2.95 build / -mcpu /
     sched flag / volatile changes it. (2.96's scheduler also puts the store early, but 2.96 codegen differs elsewhere.)
   - EABI hard-float varargs: sceSnprintf frame reserves the $f12-$f18 area but the target never stores it; ours does
     (also with K&R `__builtin_va_alist; ...`, -msingle-float, -mfp64).
